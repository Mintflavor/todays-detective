## 검토 방법

코드 전체(`app/` 23파일)를 읽고, 운영 사이트에서 **기록실 → 브리핑 → 수사 → 추리** 경로를

> 구현 단계에서는 두 가지를 실제로 검증했다. 429 경로는 리밋을 `0/hour`로 두어
> **비용 없이** 재현했고(데코레이터가 엔드포인트 진입 전에 막는다), §14는 생성

## 🔴 1. 사건 생성 실패 시 로딩 화면에 영구히 갇힌다

```
"새로운 의뢰" → phase='tutorial' + 백그라운드 생성 시작
                          ↓ 실패
      catch → console.error 만 하고 끝          useGameEngine.ts:141
                          ↓
    "수칙 확인 완료" → preloadedData 없음 → phase='loading'   :153
                          ↓
   탈출 조건: preloadedData가 채워지는 것 뿐              :88
                          ↓
                  영원히 로딩 화면
```

`LoadingScreen.tsx`에는 **버튼이 하나도 없다** (`grep -c button` = 0).
타임아웃도, 뒤로가기도, 취소도 없다. 새로고침 외에 탈출 경로가 없다.

`phase === 'loading'`을 벗어나게 만드는 코드는 아래 하나뿐이다:

```ts
// useGameEngine.ts:88
useEffect(() => {
  if (phase === 'loading' && preloadedData) finalizeGameStart(preloadedData);
}, [phase, preloadedData]);
```

### 고칠 것

- `fetchCase`의 catch에서 `setPhase('intro')`로 복구하고 에러를 표면화한다
- `LoadingScreen`에 취소/돌아가기를 넣는다 (오래 걸리는 작업이므로 30초 후 노출 등)
- 생성에 상한 타임아웃을 둔다 — 현재 프론트엔드에는 타임아웃이 없어
  Next(300초)·NPM(300초)이 끊길 때까지 로딩만 돈다

## 🔴 2. 재시도 버튼이 159원을 태우고 아무 일도 안 한다

재시도 콜백이 `generateCase` **자기 자신**이다:

```ts
// useGeminiClient.ts:62
}, "사건 파일을 불러오는데 실패했습니다.", generateCase);
```

`ErrorModal`이 이걸 호출하면(`ErrorModal.tsx:22`) API는 다시 불리지만
**반환값을 받는 곳이 없다.** `setPreloadedData`를 호출하는 것은 `fetchCase` 안의
클로저뿐이고, 재시도는 그 클로저를 거치지 않는다.

**재시도가 성공하면 159원이 청구되고 시나리오가 DB에 저장되지만 화면은 그대로 로딩이다.**

그리고 `ErrorModal`의 버튼은 **하나뿐이며 그것이 재시도다.** 닫기가 없다:

```tsx
<button onClick={() => { setErrorMsg(null); if (onRetry) onRetry(); }}>
  재접속 시도
</button>
```

실패한 플레이어가 취할 수 있는 유일한 행동이 돈을 태우는 것이다.

### 고칠 것

- 재시도 콜백을 `fetchCase`(상태를 반영하는 쪽)로 바꾼다
- `ErrorModal`에 "닫기"를 추가하고, 재시도가 없는 오류에는 재시도 버튼을 숨긴다
- 재시도 콜백이 상태를 반영하지 않는 다른 호출부가 없는지 점검한다
  (`interrogateSuspect`는 `handleSendMessageRef`로 우회하고 있어 이 문제가 없다)

## 🔴 3. 추리 평가 실패도 같은 함정 + 진행 상황이 사라진다

```ts
// useGameEngine.ts:221
setPhase('loading');           // 먼저 로딩으로
...
} catch (err) {
  setErrorMsg("추리 평가 중 오류가 발생했습니다.");
  setRetryAction(() => submitDeduction);   // phase는 되돌리지 않는다
}
```

평가가 실패하면 로딩 화면 + 재시도 전용 모달에 갇힌다. 여기서 새로고침하면
**10분간의 심문 기록이 전부 사라진다 — 진행 중 게임은 어디에도 저장되지 않는다.**

시나리오 자체는 서버에 있으므로 기록실에서 다시 열 수는 있지만, 대화 로그·AP·타이머는
전부 메모리에만 있다.

### 고칠 것

- catch에서 `setPhase('deduction')`으로 복구한다 (작성한 서술이 남아 있어야 한다)
- 최소한 `chatLogs`·`actionPoints`·`deductionInput`을 `sessionStorage`에 저장해
  새로고침을 견디게 한다

## 🔴 4. 레이트 리밋이 일반 오류와 구별되지 않는다

429·500·타임아웃이 모두 같은 문구가 된다:

```
사건 파일을 불러오는데 실패했습니다.
```

서버는 `detail`에 사유를 담아 보내는데(`lib/http.ts`의 `errorMessage`가 읽을 수 있다)
`generateCase`가 세 번째 인자로 통째로 덮어쓴다.

**"월 예산을 다 썼다"와 "네트워크가 끊겼다"는 플레이어가 취할 행동이 정반대다.**
전자는 기록실로 가면 되는데 그 안내가 없다.

리밋이 `2/hour;3/day;25/month`이므로 **429는 예외가 아니라 정상 동작이다.**
하루 4번째 방문자는 반드시 이 경로를 만난다.

### 고칠 것

- `response.status === 429`를 분기해 전용 문구를 쓴다
- `Retry-After` 헤더를 노출한다. 단 현재 `headers_enabled=False`라 slowapi가
  헤더를 넣지 않는다 (§5-C 참조 — 켜면 성공 응답이 500이 된다).
  429 응답 본문에 서버가 직접 재시도 시점을 담는 편이 안전하다
- 문구에 **"사건 기록실에서 지난 사건을 플레이할 수 있습니다"**를 넣고
  그 화면으로 가는 버튼을 모달에 붙인다

## 🟠 5. 기록실로 들어오면 튜토리얼을 못 본다

`handleLoadGame` → `finalizeGameStart` → 곧바로 `briefing`. 튜토리얼을 거치지 않는다.

**실측**: 기록실에서 사건을 열었을 때 `tutorialShown: false`, 곧바로 브리핑 렌더링.

처음 온 사람이 "사건 기록실"을 고르면 **20 AP도, 10분 제한도, 시간 초과 시 최대 B등급도
모른 채** 수사가 시작되고 타이머가 돌아간다.

기록실은 무료이고 항상 성공하는 경로이므로, **리밋에 걸린 사람이 자연히 흘러드는 곳이다.**
그런데 그 경로에 규칙 설명이 없다.

### 고칠 것

- 첫 방문 여부를 `localStorage`로 판단해 기록실 경로에서도 튜토리얼을 한 번 보여준다
- 또는 브리핑 화면에 AP·시간 규칙을 상시 요약해 둔다

## 🟠 6. 사건 카드를 클릭해도 아무 반응이 없다

**실측** (클릭 직후 DOM):

| 항목 | 값 |
|---|---|
| 로딩 표시 | 없음 |
| 카드 opacity | `1` (변화 없음) |
| 카드 `disabled` | `false` — **다시 클릭 가능** |

`loading` 상태는 있지만 전체화면 문구는 `scenarios.length === 0`일 때만 나온다:

```tsx
// LoadScenarioScreen.tsx:100
{loading && scenarios.length === 0 ? <div>문서고를 뒤지는 중...</div> : ...}
```

목록이 이미 있으면 표시가 없다. 연타하면 `onLoad`가 중복 실행된다.

### 고칠 것

- 클릭한 카드에 스피너/`disabled`/opacity 변화를 준다
- `loading` 중에는 모든 카드를 `disabled` 처리해 중복 실행을 막는다

## 🟠 7. 추리 화면에 남은 시간도 AP도 없다

**실측**: `showsTimer: false`, `showsAP: false`.

가장 중요한 결정을 내리는 화면인데 시간 초과 여부를 알 수 없다.
초과는 등급 상한(최대 B)을 결정한다.

부수적으로: **추리 화면에서는 타이머가 멈춘다** —
`isActive: phase === 'investigation' && !isTyping`이라 `deduction`에서는 정지한다.
관대한 설계지만 그것도 알려주지 않는다. 브리핑 재방문(`서류 다시보기`)도 마찬가지다.

### 고칠 것

- 추리 화면 헤더에 남은 시간과 초과 여부를 표시한다
- 초과 상태면 "최대 B등급" 경고를 제출 버튼 근처에 둔다
- 타이머가 멈추는 화면임을 알린다 (또는 의도가 아니면 계속 흐르게 한다)

## 🔵 14. 생성되는 사건이 서로 구별되지 않는다

**실측** — 현재 DB의 사건 4건 전부:

```
빗속의 재즈 클럽
빗속의 안개 저택 살인 사건
안개산장의 묵인된 죽음
안개 낀 해안 저택의 비극
```

**4/4가 안개 또는 비**다. 증거 개수도 전부 3개, 용의자 id도 전부 `[1,2,3]`.

한 판에 159원인데 생성되는 사건이 구별되지 않으면 "매일 새 사건"이라는 컨셉이
성립하지 않는다. 리밋 때문에 새 사건이 귀해진 만큼 **한 판의 신선도**가 더 중요해졌다.

또 불러온 사건은 용의자를 섞지 않는다 — shuffle이 `handleStartGame`에만 있어서
같은 사건을 다시 하면 범인 위치가 그대로다.

### 고칠 것

- 프롬프트에 분위기·장소·시대·날씨 다양성 축을 넣는다.
  생성 시 축을 무작위로 골라 주입하는 방식이 프롬프트만 고치는 것보다 확실하다
- `finalizeGameStart`에서도 shuffle한다 (또는 재플레이 시 섞는다)
- 증거 개수에 폭을 준다

## ⚪ 사소한 것

- 아이콘 전용 버튼에 `aria-label`이 없다 — 접근성 트리에 `button [ref_6]`으로만 나온다
- 푸터가 `© 2025`인데 2026년이다
- 브리핑 재방문 시에도 버튼이 "수사 시작"이라 재시작처럼 읽힌다
- 불러온 사건은 CASE ID가 `new Date().getTime()` 폴백이라 볼 때마다 바뀐다
  (`finalizeGameStart`가 `caseNumber`를 설정하지 않는다)
- 기록실 페이지네이션에 총 개수가 없다 — `scenarios.length < 10`으로만 마지막을 추정한다
- 추리 서술에 최소 길이가 없어 한 글자로도 제출된다
- `chatLogs`가 용의자 id를 `{0,1,2,3}`으로 가정한다.
  실제 시나리오 4건은 모두 `[1,2,3]`이라 **현재 문제는 없지만**, `case_data`는 의도적으로
  스키마를 걸지 않은 LLM 출력이므로(CLAUDE.md §4) id가 다르게 나오면
  `chatLogs[currentSuspectId].map`이 크래시한다. 방어 코드를 넣는 편이 낫다
- 심문 히스토리를 만들 때 `system`·`note` 역할까지 `용의자:`로 접두어를 붙인다
  (`msg.role === 'user' ? '탐정: ' : '용의자: '`) — 프롬프트에 현장 정보가
  용의자 발언으로 섞여 들어간다

## 권장 순서

**1단계 — 막힘 해소 (§1~§4).** 범위가 작고 효과가 크다.
지금은 생성이 실패하면 게임이 끝나고, 유일한 버튼이 예산을 태운다.

**3단계 — 모바일 (§10~§13).** "10분의 미스터리"는 모바일에서 플레이될 가능성이 높다.

**4단계 — 콘텐츠 다양성 (§14).** Gemini 호출이 필요하므로 예산을 보고 진행한다.

§1~§13은 전부 프론트엔드 변경이라 **Gemini 비용이 들지 않는다.**
`§14`만 생성 검증이 필요하다.

### 선행 확인 사항

`start`의 월간 카운터가 운영에서 한 번도 만들어진 적이 없다(문서 상단 참조).
§4를 고치기 전에 **429가 실제로 어떤 응답을 주는지** 확인해야 한다.
`RATE_LIMIT_START_GLOBAL`을 일시적으로 `0/hour` 같은 값으로 두고 재현하면
생성 비용 없이 429 응답을 관찰할 수 있다.

## ⚠️ 첫 수정은 실제로 고쳐지지 않았다

§1을 고쳤다고 판단하고 배포했는데, 실측에서 **데드엔드가 그대로 재현됐다.**

`handleTutorialComplete`가 `gameError`로 생성 실패를 판단했다. 그런데 사용자가
모달의 "닫기"를 누르면 `gameError`가 `null`이 되어 **실패한 사실이 사라진다.**
그 상태로 튜토리얼을 마치면 `preloadedData`도 `gameError`도 없으니 `else` 분기로
떨어져 로딩 화면에 갇혔다.

`caseFetchFailed`를 모달과 독립적인 상태로 분리해 해결했다.

**교훈**: 실패 사실과 그 실패를 알리는 UI는 수명이 다르다. UI 상태로 도메인 사실을
판단하면, 사용자가 UI를 닫는 순간 판단 근거가 사라진다.
실측하지 않았다면 "고쳤다"고 보고했을 것이다.

## 무료로 429 UX를 검증하는 방법

`RATE_LIMIT_START_GLOBAL=0/hour`로 두면 slowapi 데코레이터가 **엔드포인트 진입 전에**
막으므로 Gemini 호출이 발생하지 않는다. 비용 0원으로 리밋 UX 전체를 검증할 수 있다.

```bash
B=/mnt/user/appdata/todays-detective/compose
cp $B/.env $B/.env.bak && sed -i "s|^RATE_LIMIT_START_GLOBAL=.*|RATE_LIMIT_START_GLOBAL=0/hour|" $B/.env
cd $B && docker compose up -d todays-detective-api
# ... 검증 ...
mv $B/.env.bak $B/.env && chmod 600 $B/.env && docker compose up -d todays-detective-api
```

`scenarioId=6a8dc574bcfc6f8b5af6438d`, 35.8초, HTTP 200.

| 조건 | 폭우·안개로 고립 | **한파 경보 + 완전 단수** |
| 증거 개수 | 3개 4/4 | **2개** |
| `isCulprit` 타입 | — | **boolean** (문자열 아님) |
| 범인 수 | — | 정확히 1명, motive·trick도 그 인물만 |

즉 LLM이 주입된 지정 조건을 그대로 따랐다.

### 이 표본으로 판정할 수 없었던 것

범인이 `id 2`로 나왔는데, **지정 id가 2였는지 LLM이 지정을 무시하고 2를 골랐는지
구별할 수 없었다** — 당시 로그에 지정값이 없었다. 사전확률 1/3이라 1개 표본으로는
결론이 나지 않는다.

그래서 매 생성의 지정값과 실제 범인 위치를 로그에 남기게 했다. 앞으로는 플레이만
해도 자동으로 검증된다:

```bash
ssh unraid 'docker logs todays-detective-api --since 24h 2>&1 | grep -e "지정 조건" -e 불일치 -e 교정'
```

`범인 위치 불일치` 경고가 자주 보이면 프롬프트의 범인 지정이 먹지 않는다는 뜻이다.
그 경우에도 게임은 깨지지 않는다 (범인이 1명이면 서사가 그 인물 기준으로 일관되므로
덮어쓰지 않는다). 다만 `id 2` 편향이 돌아왔는지 확인해야 한다.
